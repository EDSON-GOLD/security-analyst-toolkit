# Automation — SQLi Login Triage (Section 03)

A small Python script that parses the lab's authentication logs and flags SQL injection login-bypass attempts. It deliberately mirrors the Sigma rules in [`02-detection-and-playbook`](../02-detection-and-playbook) — the script and the deployed detection share **one logic**, so this is the offline/triage counterpart to the live rules, not a second, divergent definition.

## Detection logic (mirrors the Sigma rules)

```
GATE:  event == "login_attempt"  AND  username contains "'"   <- the SQLi indicator
then the result field decides severity:
   result == "failed"   -> medium    (attempt, did not break in)   [sqli-login-attempt]
   result == "success"  -> critical  (auth bypass succeeded)       [sqli-login-success]
```

The single quote is the **gate**; `result` is only the discriminator *after* a SQLi attempt is confirmed. A username without `'` never trips the gate, so normal logins pass through untouched regardless of success or failure. Each finding is tagged with the id of the Sigma rule it maps back to, so an alert is always traceable to its source rule.

## How to run

```bash
# from the repo root
python3 03-automation-scripts/sqli-login-triage.py [logfile]
# default logfile: 02-detection-and-playbook/sample-logs/login-attack.log
```

## The sample log is real, not hand-crafted

The committed sample log was generated by actually attacking the Section 01 lab, not typed by hand:

1. Bring up the lab (`docker-compose up --build`) and send login traffic — both legitimate logins and SQLi payloads.
2. The app writes every attempt to `security.log` (JSON lines, via `getLogger('security')`).
3. The exported log is triaged by this script.

Verified output across all branches:

```
=== SQLi Login Triage ===
Flagged: 2  (critical: 1, medium: 1)
[CRITICAL] ...  username="' OR 1=1--"  result=success  (rule: sqli-login-success)
[  MEDIUM] ...  username="' OR 1=2-- " result=failed   (rule: sqli-login-attempt)
[CONFIRMED BREACH] 1 successful SQLi auth bypass — escalate per .../incident-playbook.md
```

Legitimate logins (`test` succeeding, `alice`/`bob` failing) appear in the log but are correctly **not** flagged — proof the gate filters on the SQLi indicator, not on the result alone.

## Known limitation & scope

- **False positive (documented, mirrors the Sigma rule):** legitimate usernames containing an apostrophe (e.g. `O'Brien`) also trip the gate. The rule flags-and-documents rather than auto-excluding, because reliably distinguishing a real apostrophe from injection at the username layer isn't dependable — the structural fix is to block `'` at registration.
- **Scope:** detection happens at the login event only. What an attacker does *after* a successful bypass is out of scope here and is covered by the incident-response playbook in Section 02.
